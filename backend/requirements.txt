# The shared package. It lives only in CodeArtifact (domain `webbpulse`,
# repository `python`, us-west-2), not on PyPI, so anything that installs this
# file needs a CodeArtifact token: CI gets one through the org reusable
# workflow, and `deploy-backend.yml` logs in before it builds.
#
# Extras, and why each one: `fastapi` for `create_app` and `run_uvicorn`,
# `dynamodb` for the secret loader and the repository base, `otel` for
# `configure_tracing`, and `aws-otel` for the SigV4-signing exporter that the
# CloudWatch X-Ray OTLP endpoint requires. Without `aws-otel` the package falls
# back to an unsigned exporter, whose 403s the OTLP exporter retries in silence,
# so the failure looks exactly like having no traffic. `testing` is a dev
# dependency and is in requirements-dev.txt.
#
# `security` is new in 0.5.0 and brings PyJWT and bcrypt, which is why neither
# is pinned below any more. `app/core/security.py` is now an adapter over
# `webbpulse.security` rather than its own implementation, and `python-jose`
# left with it: the package signs and verifies with PyJWT. An HS256 token is
# interchangeable between the two libraries and the bcrypt cost is unchanged at
# 12, so no session is invalidated and no stored hash is rewritten.
# `tests/test_security_compat.py` pins both against fixtures minted by the old
# code path.
#
# `identity` is new in 0.6.0 and brings PyJWT[crypto] and fastapi, for
# `webbpulse.identity`: the KMS signer, the JWK encoding and the `.well-known`
# router that the identity standard's M0 spike serves. It is deliberately not a
# dev-only extra even though the spike is throwaway, because the code that
# imports it runs in the deployed identity function.
#
# It does not bring boto3. The module takes a KMS client rather than
# constructing one, so the caller owns that dependency, and boto3 is already
# here through `dynamodb`.
#
# 0.7.0 adds `webbpulse.log_context` and `webbpulse.metrics`, both standard
# library only and both in the base install, so neither is a new extra.
# `log_context` is what removed `aws-lambda-powertools` from the line below it.
# Powertools' correlation is `@logger.inject_lambda_context`, a decorator on a
# Lambda handler, and there is no handler here: the Web Adapter turns each
# invoke into an HTTP request against a uvicorn process, so the decorator never
# ran and every log line carried no correlation id. `RequestIdMiddleware` binds
# a ContextVar instead and `JsonFormatter` merges it, which is the same
# correlation actually reaching the log group. Nothing else imported Powertools.
#
# 0.8.0 is adoption ergonomics and is additive: nothing changes for a caller
# that passes no new argument. What this backend takes from it is
# `webbpulse.http.user_id_dependency`, which fixes the sync dependency trap that
# PR 153 worked around locally by making `get_current_user` `async def` and
# calling `set_user_id` inside it. The binding is the package's now, so the
# resolver goes back to being only a resolver. The other two additions,
# `configure_logging(stream=, formatter=)` and `metrics_enabled_from_env`, are
# not adopted: this backend has no local logging wrapper overriding either of
# those and emits no metrics at all, so there is nothing here for them to
# replace.
#
# 0.9.0 is identity milestone M1, and it is additive in the strict sense: the
# only entry in its Changed section is that `src/webbpulse/identity.py` became
# `src/webbpulse/identity/tokens.py` with `webbpulse.identity` re-exporting the
# entire M0 surface, so `identity_router` and `public_jwk_from_kms`, the two
# names the M0 spike wiring imports, are importable from exactly where they
# were. Nothing in this repository changed to take the bump: the full suite
# passes against 0.9.0 with no source edit, which is the check that the
# re-export claim holds rather than a claim about it.
#
# What the bump makes available, and what PR B mounts, is the rest of M1:
# `IdentitySettings` as a validated `BaseSettings` on the `IDENTITY_` prefix,
# `IdentityHooks`, the storage interfaces, `TokenService` with rotation across
# several keys, `authorizer_claims()` for reading what the gateway authorizer
# leaves on the request, and `build_identity_router`, which serves the two
# `.well-known` documents and `/health` with the Cache-Control headers the
# standard's section 3.4 specifies. The `identity` extra is unchanged at
# `PyJWT[crypto]` and `fastapi`, so this line gains no dependency.
#
# 0.10.0 is identity milestone M2: the password and session flows, plus the
# progressive lockout and the password policy behind them. Additive for a
# consumer that mounts only the documents, and this one no longer is: PR B
# supplies hooks and a credential store, so the six POST flow routes mount.
#
# One breaking change matters here, and it is the one this repository reported.
# Every route now mounts under the issuer's path, derived inside the package by
# `identity_prefix(settings)`, rather than at the origin. 0.9.0 served the two
# `.well-known` documents at the origin whatever the issuer said, and the
# workaround was to mount the router with `prefix="/api/auth"` in
# `app/composition/wiring.py`. That prefix is removed in this change, because
# leaving it would double every route to `/api/auth/api/auth/...`. The
# `identity_mount_prefix` helper that computed it is gone with it: the package
# derives the prefix now, so a second implementation here could only disagree.
#
# `cookie_path` also defaults to the issuer's path rather than a literal
# `/api/auth`, which needs no change here: the issuer already carries that path,
# so the derived value is the one this product was going to set by hand.
#
# 0.11.0 is identity milestone M3: email verification and password reset over
# SES. Strictly additive. The four new routes mount only when a product supplies
# both an `EmailSender` and an `identity-tokens` store, on the same rule the M2
# flow routes follow, so a service supplying neither mounts exactly what it
# mounted in 0.10.0. This one supplies both, so all four mount.
#
# What the bump makes available: `webbpulse.identity.email` with the
# `EmailSender` seam, `SesV2EmailSender` over SES v2 `SendEmail` and
# `RecordingEmailSender` for tests; `webbpulse.identity.verification` with
# `LinkService`, the single-use link both flows are built on; the
# `identity-tokens` store in both its Dynamo and in-memory forms; and
# `IdentityHooks.mark_email_verified`.
#
# `mark_email_verified` is the one part of the bump that is not free. It is the
# only hook with no default, deliberately, because a product that mounted the
# flow and forgot it would confirm addresses that never became verified. It is
# implemented in `app/composition/identity_hooks.py` in this change.
#
# The `identity` extra is unchanged. `SesV2EmailSender` takes a client rather
# than building one and types it structurally, so the extra still does not
# depend on boto3, and the templates use `string.Template` from the standard
# library rather than adding a templating dependency. This line gains nothing.
#
# 0.12.1 is identity milestone M4: TOTP, recovery codes, the MFA ticket, step
# up, and `amr` on the access token. Additive on the same rule every milestone
# before it followed. The six MFA routes mount only when `totp_enabled` is on
# and the product supplies a TOTP factor store, a recovery code store and an
# identity-tokens store, so a service supplying none of them mounts exactly
# what it mounted in 0.11.0. This one supplies all three, so all six mount.
#
# The one behaviour change is confined to a user who has actually enrolled: for
# a user with an **active** factor, `login` answers 200 with a challenge,
# `{"mfa_required": true, "mfa_ticket": "...", "factors": ["totp"]}`, instead of
# tokens, and the caller finishes at `POST /api/auth/login/totp` with
# `{"mfa_ticket", "code"}`. Nobody is enrolled today, so nothing about the
# current login changes until somebody enrols.
#
# What the bump makes available: `webbpulse.identity.totp`, RFC 6238 TOTP with
# no new dependency; `webbpulse.identity.crypto` with `EnvelopeCipher`, which
# seals a seed under a data key from KMS so the stored seed is unreadable to a
# principal holding only `dynamodb:Query`; `webbpulse.identity.mfa` with
# `MfaService`; and the two M4 stores in both their Dynamo and in-memory forms.
#
# THE `identity` EXTRA GAINS NOTHING, and that is worth stating because envelope
# encryption and TOTP both sound like they would want a library. TOTP is `hmac`
# and `struct` from the standard library, and the envelope is `cryptography`
# through `PyJWT[crypto]`, which the extra already carries for the JWK. So the
# line below is unchanged apart from its version, and no new extra is added.
#
# 0.12.1 over 0.12.0 is one fix with no behaviour change for a caller that does
# nothing: `webbpulse.security.hash_password` reads `DEFAULT_ROUNDS` at call
# time rather than freezing it into a default argument at import. The cost is
# still 12 and every hash this repository has written still verifies.
# 0.13.0 is an identity M4 security fix, and it is the first breaking change in
# this line since 0.10.0 moved the routes under the issuer path. `POST
# /api/auth/totp/disable` and `POST /api/auth/recovery-codes` now require
# `{"code": "..."}` in the body: a current TOTP code or an unused recovery code,
# on top of the bearer access token both already required. Both routes are
# destructive to the second factor and both were reachable with a stolen access
# token alone, which is a token that could switch off the control bounding what
# stealing it is worth, or burn the recovery codes the real user would need to
# get back in.
#
# The code goes through `MfaService.verify_challenge`, the same call the second
# leg of login already makes, so there is no second verification path: a TOTP
# code and a recovery code are both accepted, the replay watermark is the one
# already in place, and a recovery code spent on either route is consumed
# exactly as it is on login. Verification happens before anything is deleted, so
# a refused disable leaves the factor active and a refused regenerate leaves
# every existing code working. There is deliberately no step-up alternative:
# accepting a recently stepped up token would reopen the same door.
#
# A missing, non-string or blank `code` is a 422 `VALIDATION_ERROR` rather than
# an `INVALID_MFA_CODE`, so a client that forgot the field is told that instead
# of showing the user "that code is not valid" for a request that never asked
# for one. A wrong code is the 401 `INVALID_MFA_CODE` envelope `login/totp`
# answers, and both routes now carry that route's `mfa-verify` rate limit,
# because they accept the same codes.
#
# WHAT CHANGES IN THIS REPOSITORY IS NOTHING AT RUNTIME, and that is worth
# stating for a breaking change. Nobody is enrolled, so neither route has a
# caller yet; no stored data changes shape, so there is no migration; and the
# body is the package's contract with whoever calls it, which is the frontend
# rather than this backend. `app/composition/identity.py` supplies the same
# three stores it supplied under 0.12.1 and passes no new argument. The `identity`
# extra is unchanged, so this line gains no dependency. What this bump costs here
# is the two docs describing those routes, and `tests/test_identity_m4.py` gains
# the route-contract checks for the new body.
